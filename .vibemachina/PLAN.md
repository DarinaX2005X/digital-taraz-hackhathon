# Tirlik: полный план v3

Концепция согласована. Этот полный пакет ожидает явного утверждения пользователя. До него разрешены только чтение, проверка выполнимости, плановые документы, эскиз айдентики и локальная инфраструктура VibeMachina. Продуктовый код, scaffold и назначения на реализацию не начинать.

## Обещанный результат

Адаптивная агентная система для малого и среднего бизнеса разных отраслей: собственные материалы/ресурсы -> свободная цель -> предметные действия и точный расчёт -> проверенный вариант -> одобренное клиентское предложение -> заказ/запись с общим резервом -> исполнение -> честный факт и новый цикл. Это полноценные рабочие панели и реальные операции, не chatbot над файлами, не фиксированное меню кампаний и не абстрактные агенты.

Название Tirlik, слоган «Превращайте запасы и свободные часы в заказы». Публичный сайт, личное пространство, владелец/управляющий/сотрудник/клиент, изолированное демо, три языка ru/kk/en, сохранение/возврат/редактирование/сравнение/экспорт, реальная AI-работа, Vercel deploy, verified README, описание, презентация и законченный видео-ролик включены в объём. Этап 03 является ранней проверкой риска, а не границей поставки.

## Общие договорённости

PROJECT C1 отвечает за адаптивность; C2 за stack/env/hosting; C3 за entities/DTO/formats; C4 за вычисления; C5 за версии/транзакции/состояния; C6 за AI/durable/cost; C7 за роли/privacy/auth; C8 за routes/API/errors; C9 за demo/first session; C10 за поставку. Каждая задача обязана применять relevant contracts, не изобретать локальную несовместимую копию.

Next.js/TypeScript, PostgreSQL/Drizzle, Better Auth, private Blob, Workflow SDK, OpenRouter, typed domain tools, ru/kk/en. Local PostgreSQL+Mailpit в Docker, explicit local file adapter; production Vercel+Neon+private Blob+Workflows+SMTP. Доступ к Vercel сообщил пользователь; CLI существует, actual account/service permissions ещё не доказаны. Доступы/лимиты проверяются в 01.1 и настоящем раннем пути 03.1/03.3, не в последний день. Никаких платных подписок без разрешения.

Ключ OpenRouter уже помещён пользователем в env, основная модель xiaomi/mimo-v2.5. Разрешена недорогая замена по модальности/поддержке функций. GPT/OpenAI, Claude/Anthropic и дорогие/непроверенные по цене fallback исключены; allowlist/capability и бюджет проверяются сервером. Ключ никогда не печатать. Числовые лимиты C6 являются предложенными guardrails; увеличение требует отдельного согласования.

Нет заранее доступной базы местных компаний. Рабочие данные приносит конечный пользователь; наши fixtures явно синтетические. Не выдавать пример за полученный доход, прогноз за факт или shared capacity за независимую ёмкость каждого предложения. Нет автоматической рассылки в чужие соцсети, подключённого эквайринга, ERP/налоговой сертификации и рыночного прогноза из воздуха. Неподдерживаемая внешняя операция честно обозначается и оставляет полезный подготовленный результат.

## Порядок и параллельность

1. 01.1 создаёт общие контракты; 01.2 и 01.3 могут идти параллельно в своих путях. 02.1 передаёт auth context; 02.2 и 02.3 независимы, 02.4 следует ресурсному движку.
2. 03.1 может начаться после ingestion/auth, пока заканчивается simulation; 03.2 требует обе части. 03.3 проверяет настоящий input-to-AI-to-persisted-result и ранний Vercel preview. Это обязательный риск-рубеж до наращивания всех интерфейсов.
3. После 03.3 задачи 04.1/04.2/04.3 и 06.1 могут работать параллельно по отдельным путям. В 05 публикация -> checkout -> исполнение -> outcomes последовательно зависят от доменных контрактов; интерфейсные подшаги могут подготавливаться только без несовместимых mock-обещаний.
4. 06.2 требует полного demo domain loop, 06.3 объединяет first session. 07.1 и 07.3 после своих явных зависимостей могут пересекаться с 06; 07.2 после событий.
5. 08.1/08.2 независимы и read/test-oriented. 08.3 получает эксклюзивное владение repair paths после их результатов. 09 выполняется последовательно: независимое ревью, исправление, повторная проверка.
6. 10 production -> проверенный README/чистый запуск -> описание. 11.1 презентация и 11.2/11.3 видео могут идти параллельно после стабильного README. 11.4 ждёт оба готовых материала; 12 проверяет всю поставку после последнего deploy.

Точный граф задают Depends on, а не только номера этапов. Межэтапное перекрытие допустимо лишь перечисленное здесь, после проверки активных write paths MAIN. Ориентир пользователя около недели, без выдуманной точной даты; работа непрерывно движется по готовым зависимостям. Это не основание сокращать объём до раннего прохода.

## Договор делегирования

MAIN отвечает за общий продукт, canonical memory, Git, интеграцию и утверждение checkpoints. Каждая содержательная implementation задача выполняется SUBAGENT с исключительными write paths; отдельные пользовательские чаты не создаются. Не назначать worker владельцем всей VibeMachina. Shared package.json/lockfile/config, DB migration registry/snapshot, shell route registry и root i18n изменения только через короткий loan MAIN после сдачи предыдущего writer. Feature-owned schema, translations, tests и services находятся в своих каталогах.

Динамические Next route adapters в src/app с параметрами [locale]/[workspaceId]/[id] интегрирует MAIN последовательно из переданных feature exports. Точные adapter paths указаны под Paths соответствующих задач, но не входят в параллельные write zones работников. Функциональная логика страниц и handlers остаётся у SUBAGENT в feature-папке; MAIN добавляет только тонкую маршрутизацию или выдаёт отдельный исключительный loan, фиксируя его перед записью. Это исключает гонки общего дерева маршрутов при параллельной разработке.

Обязательный dispatch packet содержит полный исходный BRIEF, все последующие дословные пользовательские поправки, relevant original TESTING entries, PROJECT, DESIGN и конкретную stage task, нужные skill references, exclusive paths/dependencies/test commands. Краткое описание задачи не заменяет исходный текст. Для product/UI/UX/video требование полной глубины особенно важно: пользовательские слова о механизме, свободе постановки, композиции, панелях, motion/референсах передаются без сжатия. Если вывод чтения обрезан, агент дочитывает диапазоны; MAIN проверяет подтверждение существенных ограничений. Новое замечание активному исполнителю пересылается целиком с контекстом.

Все UI workers читают foundation, ux и anti-slop плюс DESIGN. AI workers engineering core/integrations/ai/chat по предмету; media workers полный media contract и оригинальные референсы. Единственное намеренное ограничение пакета: первый слепой проход reviewer09.1 получает полный BRIEF и код, но не наши плановые интерпретации; второй проход получает их.

## Checkpoint и частые коммиты

Каждый checkpoint даёт законченную проверяемую часть с конкретным результатом и тестами. В длинной задаче несколько промежуточных коммитов; не ждать всего этапа или конца дня. Worker передаёт MAIN изменённые пути, что завершено, commands/results, актуальные риски и продолжение, останавливает запись в сдаваемые файлы. MAIN проверяет diff/tests/TESTING и коммитит только эти пути. Маленькие связанные edits можно объединить; полуработающую миграцию или чужой незавершённый код коммитить ради частоты нельзя.

Только MAIN stages/commits/pushes через штатный C:/Users/user/.codex/skills/vibemachina/scripts/checkpoint.mjs с реальным check contract, явными --paths и --push. Не подменять команду ручным Git или новым wrapper; repository-contained scripts/checkpoint-check.mjs отвечает только за проверки. Локальный config в .vibemachina/runtime/checkpoint.json: сейчас planning validation/Git hygiene, после01.1 настоящие type/lint/domain/build checks. Intended upstream origin/main проверен; force не используется. Последнее указание пользователя разрешает VibeMachina в Git, кроме runtime/, BRIEF.md и TESTING.md; .env также ignored. План, спецификации, дизайн, задачи и STATE публикуются с ясным pending approval, никогда git add -f для приватных путей. Содержательные public code/docs/assets коммитятся часто, без пустых коммитов для счётчика.

## Проверки и обратная связь

Агенты: typecheck/lint/build, unit/DOM-semantic без браузера, real PostgreSQL concurrency, parser/schema/property/domain, HTTP/API, true economical AI capability/evals, SMTP/storage/Workflow persistence и deploy/clean-start probes. Mock и live evidence строго различаются. Не использовать CUA, Playwright, Selenium, Puppeteer, headless browsers или эквиваленты, включая через shell/worker/renderer. Не открывать вкладки автоматически.

Пользователь: внешний вид, реальный browser interaction, keyboard/touch/zoom/mobile, выбор даты, читаемость источника/сравнения, видео playback. MAIN даёт точные URL и ожидаемые действия, не повторяет его визуальный обзор. Читать TESTING после каждой задачи, перед dispatch/checkpoint и при естественной паузе 10–15 минут длительной работы. Сохранять исходные записи. Visual fix = needs-user-check, пока пользователь не подтвердит. Присланные изображения и исходные media-reference файлы можно анализировать; это не разрешение снимать приложение.

Независимый plan reviewer один раз читает полный BRIEF+PROJECT+DESIGN+PLAN+stages+PLAN-HUMAN на пропавшие/поверхностные требования. check-plan.mjs проверяет структуру, двусторонние ссылки, граф и ownership, но не заменяет содержательное чтение.

## Условия приёмки всего продукта

Сквозной механизм реально проходит на физических, временных и смешанных ресурсах; новая свободная цель меняет агентные операции, а не только заголовок шаблона. Shared-resource atomicity, tenant/privacy, permissions/approval/version/fencing и economical budget проверены. Все роли и состояния полезны, аккаунт/возврат/демо/локали/экспорты завершены. UI acceptance честно отделена от автоматических checks.

Публичный Vercel URL с постоянными DB/files/jobs и работающей почтой, GitHub без секретов, BRIEF, TESTING и runtime, воспроизводимый README, название/русское описание, презентация и полный video с постером/субтитрами и встраиванием. Разрешённые плановые документы VibeMachina могут быть в репозитории, но запуск продукта от них не зависит. Не помечать всё готовым при отсутствующих обязательных сервисах/материалах или неисполненном требовании. Внешние blockers требуют конкретного действия/доступа, не фиктивной замены.

После предъявления пакета STATE = awaiting-approval, Approval = pending. Нужен отдельный явный ответ об утверждении полного плана; сообщения о ключе, модели или коммитах сами по себе его не утверждают.
